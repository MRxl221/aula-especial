Do diretório local ao repositório no GitHub

Vocês têm uma pasta com código que funciona na máquina. Ao final deste roteiro, essa pasta vira um repositório no GitHub com histórico de commits, testes automatizados, checagem automática (CI) a cada envio e um fluxo de trabalho com branch e pull request.

Cada passo mostra onde ele roda: PowerShell VS Code Navegador GitHub. Marque a caixa quando concluir. A página não guarda o progresso no computador, porque o laboratório é compartilhado: se fechar a aba, remarquem o que já fizeram.

Contexto da atividade

Sistema
Windows 10/11, PowerShell 5.1 ou 7
Ferramentas
Git 2.40+, Node.js 20 LTS+, VS Code, conta no GitHub
Grupos
2 a 4 estudantes, um computador por grupo
Duração
2 aulas de 50 min (aula 1: etapas 0 a 3 · aula 2: etapas 4 a 7)
  • Piloto(a): digita os comandos no PowerShell e edita no VS Code.
  • Navegador(a): lê o passo em voz alta e confere o “resultado esperado” antes de marcar.
  • Guardião(ã) do repositório: confere o git status antes de cada commit e garante que nenhum segredo vai para o GitHub. Em grupos de 4, a quarta pessoa é relator(a) e anota erros e soluções.

Troquem os papéis a cada etapa. Quem for dono(a) da conta do GitHub usada no push deve adicionar os colegas como colaboradores (passo 24).

Qual é a situação da pasta de vocês?

Para descobrir, abra o PowerShell na pasta e rode Test-Path .git. True = cenário B; False = cenário A. A lista de passos e a barra de progresso se ajustam à escolha.

Recursos necessários

Marque cada item quando estiver disponível no computador do grupo. Os recursos contam no progresso.

Depois de instalar qualquer programa com winget, feche e abra o PowerShell de novo. Sem isso o terminal não enxerga o comando novo.

ETAPA 0

Preparar o ambiente

01PowerShell
PowerShell
git --version
node -v
npm -v
code --version

git version 2.4x…, v20.x ou maior, um número para o npm e três linhas para o VS Code. Se algum disser “não é reconhecido”, volte aos recursos.

02PowerShell

O nome e o e-mail aparecem em cada commit. Use o mesmo e-mail da conta do GitHub, para que os commits fiquem ligados ao perfil.

PowerShell
git config --global user.name "Seu Nome Completo"
git config --global user.email "seu-email-do-github@exemplo.com"
git config --global init.defaultBranch main
git config --global core.autocrlf true
git config --global --list

init.defaultBranch main faz o git init já criar a branch main, que é o padrão do GitHub. core.autocrlf true converte fins de linha do Windows (CRLF) para o formato do repositório (LF).

Computador compartilhado: antes de configurar, rode git config --global --list. Se aparecer o nome de outra pessoa, substitua pelo seu. No final da aula, o passo 27 apaga tudo.

03PowerShellVS Code
PowerShell
cd C:\projetos\meu-projeto      # troque pelo caminho real
Get-ChildItem -Force
code .

O PowerShell lista os arquivos do projeto e o VS Code abre a mesma pasta. Todos os comandos seguintes rodam nesta pasta.

ETAPA 1

Limpar e organizar a pasta antes do primeiro commit

Tudo o que entrar no primeiro commit fica no histórico para sempre, mesmo que seja apagado depois. Por isso a limpeza vem antes do git init.

04PowerShell
PowerShell
Get-ChildItem -Recurse -File -Exclude *.png,*.jpg |
  Where-Object { $_.FullName -notmatch '\\node_modules\\|\\.git\\' } |
  Select-String -Pattern 'senha|password|token|api[_-]?key|secret' |
  Select-Object Path, LineNumber, Line

Para cada resultado, decidam: é um segredo de verdade? Se for, tire o valor do código e leve para um arquivo .env (que não vai para o GitHub). No código, leia com process.env.NOME_DA_VARIAVEL.

Nenhum valor real de senha ou token sobrou dentro de arquivos .js, .html ou .json.

05VS Code

Crie o arquivo .gitignore na raiz da pasta (o nome começa com ponto e não tem extensão) com este conteúdo:

.gitignore
# dependências (o npm baixa de novo com npm install)
node_modules/

# segredos e configurações locais
.env
.env.*
!.env.example

# arquivos gerados
dist/
build/
coverage/
*.log

# sistema e editor
Thumbs.db
Desktop.ini
.DS_Store

A linha !.env.example abre uma exceção: o modelo sem valores reais pode ir para o GitHub.

06VS Code

O README é a primeira coisa que aparece na página do repositório. Adapte o modelo:

README.md

Uma frase dizendo o que o sistema faz e para quem.

## Como rodar
1. Instale o Node.js 20 LTS ou superior.
2. `npm install`
3. Copie `.env.example` para `.env` e preencha os valores.
4. `npm start`

## Como testar

- Nome 2 (@usuario-github)
.env.example (só os nomes, sem valores reais)
PORTA=3000

Se o projeto não usa nenhuma variável de ambiente, pule o .env.example e marque o passo.

ETAPA 2

Garantir que existem testes e que eles passam

Código migrado sem teste é código que ninguém sabe se ainda funciona. O GitHub vai rodar estes mesmos testes sozinho na etapa 5.

07PowerShellVS Code
PowerShell
if (-not (Test-Path package.json)) { npm init -y }
code package.json

Deixe a seção scripts assim (mantenha os que já existiam, como start):

package.json (trecho)
"type": "module",
"scripts": {
  "start": "node src/index.js",
  "test": "node --test"
}

node --test encontra sozinho os arquivos terminados em .test.js. Se o projeto já usa require() (CommonJS), não adicione "type": "module" e use require no teste do passo 08.

08VS Code

Escolham uma função do projeto que recebe um valor e devolve um resultado. Testem o caso normal e um caso de borda (valor vazio, zero, texto inválido). Exemplo com uma função calcularDesconto em src/precos.js:

tests/precos.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { calcularDesconto } from '../src/precos.js';

test('aplica 10% de desconto', () => {
  assert.equal(calcularDesconto(200, 10), 180);
});

test('desconto zero mantém o preço', () => {
  assert.equal(calcularDesconto(50, 0), 50);
});

test('recusa preço negativo', () => {
  assert.throws(() => calcularDesconto(-5, 10));
});

Troquem o nome da função, o caminho do import e os valores pelos do projeto de vocês. A função precisa estar exportada (export function …).

09PowerShell
PowerShell
npm test

No final da saída aparecem # pass 3 e # fail 0 (o número de pass é a quantidade de testes de vocês). Se algum falhar, corrijam o código ou o teste antes de continuar: não se envia para o GitHub o que já está quebrado.

ETAPA 3

Versionar localmente

10PowerShell
PowerShell
git init
git status

Initialized empty Git repository e, no status, On branch main com os arquivos em vermelho em “Untracked files”.

10PowerShellCenário B
PowerShell
git status
git log --oneline --graph -15
git branch -a
git remote -v
  • Se a branch principal se chama master, renomeie: git branch -M main.
  • Se git remote -v mostra um endereço antigo (outra conta, GitLab, Bitbucket), guarde-o com outro nome: git remote rename origin antigo.
  • Se o .gitignore novo pegou arquivos que já estavam versionados (ex.: node_modules), tire do índice sem apagar do disco: git rm -r --cached node_modules.

Se algum commit antigo contém uma senha real, apagar o arquivo agora não resolve: ela continua no histórico. Troquem a senha no serviço de origem (revogar o token) e avisem o professor antes do push.

11PowerShell
PowerShell
git add -A
git status
git diff --cached --stat

O(a) guardião(ã) lê a lista em voz alta. Precisam aparecer: .gitignore, README.md, package.json, a pasta src e a pasta tests.

Não aparecem node_modules/, .env nem arquivos .log. Se aparecerem, revejam o .gitignore e rodem git rm -r --cached NOME.

12PowerShell

Usamos o padrão Conventional Commits: um tipo, dois pontos e uma frase curta no imperativo. O segundo -m é o corpo, que explica o porquê.

PowerShell (cenário A)
git commit -m "chore: versão inicial do projeto" -m "Inclui código-fonte, testes com node:test, README e .gitignore."
git log --oneline
PowerShell (cenário B: só os ajustes de organização)
git commit -m "chore: organiza projeto para publicação no GitHub" -m "Adiciona .gitignore, README e testes; remove node_modules do versionamento."
git log --oneline -5
feat:funcionalidade novafix:correção de erro
docs:documentaçãotest:testes
chore:organização, configuraçãoci:checagem automática

O git log --oneline mostra o commit com um código curto (hash) e a mensagem. Se aparecer “Author identity unknown”, volte ao passo 02.

ETAPA 4

Criar o repositório no GitHub e enviar o código

13NavegadorGitHub
  1. Entre em github.com/new com a conta de quem será dono(a).
  2. Repository name: nome curto, minúsculo, com hífens (ex.: calculadora-descontos).
  3. Description: a mesma frase do README.
  4. Escolha Public (portfólio) ou Private (combine com o professor).
  5. Não marque “Add a README”, “.gitignore” nem “license”. O repositório tem que nascer vazio, porque esses arquivos já estão no commit local.
  6. Clique em Create repository e copie o endereço HTTPS (https://github.com/USUARIO/NOME-DO-REPO.git).

Atalho com o GitHub CLI, que cria, conecta e envia de uma vez (substitui os passos 13 a 15): gh auth login e depois gh repo create NOME-DO-REPO --private --source . --remote origin --push.

14PowerShell
PowerShell
git remote add origin https://github.com/USUARIO/NOME-DO-REPO.git
git remote -v

Duas linhas com origin, uma terminando em (fetch) e outra em (push). Se aparecer “remote origin already exists”, troque o endereço com git remote set-url origin URL.

15PowerShellNavegador
PowerShell
git push -u origin main

Na primeira vez, o Git Credential Manager abre uma janela: escolha Sign in with your browser e autorize no GitHub. O GitHub não aceita mais a senha da conta no terminal.

branch 'main' set up to track 'origin/main'. O -u liga a branch local à remota; daqui em diante basta git push.

Cenário B com outras branches: git push -u origin --all e git push origin --tags enviam todas.

16NavegadorGitHub

Atualize a página do repositório e confiram, item por item:

  • O README aparece formatado abaixo da lista de arquivos.
  • O número de commits é o mesmo do git log --oneline local.
  • Não existe pasta node_modules nem arquivo .env.
ETAPA 5

Checagem automática (CI) com GitHub Actions

17PowerShellVS Code
PowerShell
New-Item -ItemType Directory -Force .github\workflows | Out-Null
code .github\workflows\ci.yml
.github/workflows/ci.yml
name: Checagens automáticas

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  testes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Instalar dependências
        run: npm install
      - name: Testes automatizados
        run: npm test

No YAML a indentação é feita com espaços, nunca com Tab. Um espaço fora do lugar invalida o arquivo.

18PowerShell
PowerShell
git add .github/workflows/ci.yml
git commit -m "ci: roda os testes automaticamente no GitHub Actions"
git push
19NavegadorGitHub

No repositório, abra a aba Actions e clique na execução “ci: roda os testes…”. Abra o passo “Testes automatizados” e comparem com a saída do passo 09.

Bolinha verde ao lado do commit, com a mesma contagem de testes que apareceu na máquina de vocês.

Experimento (opcional): mudem um valor esperado no teste, façam commit e push, vejam o X vermelho, desfaçam com git revert HEAD e enviem de novo.

ETAPA 6

Trabalhar em equipe: branch, pull request e versão

Daqui para frente, ninguém altera a main direto. Cada mudança nasce em uma branch, passa pela CI e pela revisão de um colega, e só depois entra na main.

20NavegadorGitHub

Dono(a) do repositório: Settings › Collaborators › Add people e informe o usuário de cada colega. Cada um aceita o convite pelo e-mail ou em github.com/notifications.

21PowerShellVS Code
PowerShell
git switch -c docs/instrucoes-de-teste
code README.md                 # acrescente o que o teste verifica
npm test
git add README.md
git commit -m "docs: explica o que os testes verificam"
git push -u origin docs/instrucoes-de-teste

O terminal mostra um link “Create a pull request for 'docs/instrucoes-de-teste' on GitHub”.

22NavegadorGitHub
  1. Clique em Compare & pull request. Preencha: o que mudou, por que mudou e como testar.
  2. Esperem a CI ficar verde na própria PR.
  3. Outro integrante abre Files changed e comenta usando os rótulos da aula de Code Review: bloqueante:, sugestão:, pergunta: e elogio:.
  4. Com aprovação (Approve) e CI verde: Merge pull request e depois Delete branch.
23PowerShell
PowerShell
git switch main
git pull
git branch -d docs/instrucoes-de-teste
git log --oneline --graph -6

O log mostra o commit de merge da PR no topo da main local.

24NavegadorGitHub

Settings › Branches › Add branch ruleset (ou “Add classic branch protection rule”) para main, marcando:

  • Exigir pull request antes do merge, com 1 aprovação.
  • Exigir que a checagem testes passe.

Em contas gratuitas, a regra vale para repositórios públicos. Em repositório privado, ela exige plano pago ou o Student Developer Pack; se não tiverem, combinem a regra entre vocês e marquem o passo.

25PowerShellGitHub
PowerShell

git push origin v1.0.0

No GitHub, a tag aparece em Releases › Tags. Lá é possível transformá-la em release com notas da versão. O formato MAIOR.MENOR.CORREÇÃO é o versionamento semântico.

Problemas comuns

Erros que costumam aparecer no laboratório e como resolver. O(a) relator(a) anota qual deles o grupo encontrou.

'git' não é reconhecido como nome de cmdlet…

O Git foi instalado com o PowerShell aberto. Feche todas as janelas do terminal e abra de novo. Se continuar, reinstale com winget install --id Git.Git -e.

npm : … npm.ps1 não pode ser carregado porque a execução de scripts foi desabilitada

Política de execução do Windows. Libere só para esta janela, sem alterar o computador:

PowerShell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

Outra saída é chamar npm.cmd test em vez de npm test.

Author identity unknown / Please tell me who you are

Faltou o passo 02. Configure user.name e user.email e repita o commit.

error: src refspec main does not match any

Não existe commit ainda, ou a branch se chama master. Confira com git log --oneline e git branch. Se for master: git branch -M main.

! [rejected] main -> main (fetch first)

O repositório no GitHub foi criado com README ou licença e tem um commit que a máquina local não tem. Traga esse commit e reenvie:

PowerShell
git pull --rebase origin main
git push -u origin main

Nunca usem git push --force na main para “resolver” isso: apaga o trabalho do remoto.

remote: Permission to USUARIO/REPO.git denied … 403

O Windows guardou o login de outra pessoa. Remova a credencial (cmdkey /delete:git:https://github.com) e rode o push de novo para logar com a conta certa. Se a conta certa é de um colega, ele precisa adicionar vocês como colaboradores (passo 20).

warning: in the working copy of '…', LF will be replaced by CRLF

É só um aviso do core.autocrlf. Pode seguir normalmente.

A pasta node_modules (ou o .env) foi para o GitHub

Inclua no .gitignore e tire do versionamento sem apagar do disco:

PowerShell
git rm -r --cached node_modules .env
git commit -m "chore: remove arquivos que não devem ser versionados"
git push

Se foi o .env com uma chave real, ela continua visível no histórico. Revoguem a chave no serviço que a gerou e criem outra.

A CI ficou vermelha, mas na minha máquina passa

Abra o log na aba Actions. Causas comuns: arquivo com nome em maiúscula/minúscula diferente do import (o Linux da CI diferencia, o Windows não), dependência instalada só localmente sem estar no package.json, ou teste que depende do .env.
